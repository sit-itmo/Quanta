# ESP8266 / MCU: активный порт 0.5.0

## Активный порт и сохранённые метрики

За основу взяты именно MCU-добавления `inv-0.2.2.zip`; архив
`inv-0.2.2-windows-src(1).zip` служит исходной pre-MCU базой сравнения.
Все девять ключей сохранены в активном `metrics/mcu.def`:

| Ключ | Получение / смысл |
|---|---|
| `mcu.heap.free_bytes` | `esp_get_free_heap_size()` |
| `mcu.heap.min_free_bytes` | `esp_get_minimum_free_heap_size()` |
| `mcu.cpu.freq_mhz` | `configCPU_CLOCK_HZ / 1000000`, configured/estimated, не измерение |
| `mcu.power.vdd_mv` | `esp_wifi_get_vdd33()`, корректное преобразование в mV; opt-in |
| `mcu.cores` | `esp_chip_info()` |
| `mcu.revision` | `esp_chip_info()` |
| `mcu.chip_id` | Младшие 24 bits factory MAC из `esp_efuse_mac_get_default()` |
| `mcu.flash_embedded` | `CHIP_FEATURE_EMB_FLASH` |
| `mcu.sdk_version` | `esp_get_idf_version()` |

SDK-метрики намеренно **не используют HAL**. GPIO находится отдельно в hardware HAL.
OS-слой метрик порта сохранён: имя SDK, kernel release/version, arch=xtensa, hostname,
uptime, online CPUs. Load average возвращает UNSUPPORTED. Каталог содержит 22 descriptors (9 OS, 9 MCU, 4 общих quanta/HAL);
наличие descriptor не означает поддержку каждого поля данной платформой.
Serial-приложение печатает все 9 MCU полей плюс os.name/os.hostname/os.uptime каждые 2 секунды.

| В исходном MCU-архиве | В активном дереве 0.5.0 |
|---|---|
| `src/firmware/esp8266/` | `firmware/esp8266/` |
| `components/inv/` | `components/quanta/` + `cmake/esp8266_sources.cmake` |
| `src/providers/mcu.c` | `sensors/platform/esp8266/mcu_metrics.c`, прямые callbacks |
| `src/hal/esp8266/mcu.c` | `sensors/platform/esp8266/mcu.c` |

| `src/platform/freertos/freertos.c` | `osal/freertos/freertos.c` |
| `src/platform/freertos/thread.c` | `osal/posix/thread.c`, SDK pthread/condition API |
| `metrics/mcu.def` | `metrics/mcu.def`, все 9 ключей |
| `sdkconfig`, `sdkconfig.defaults` | Exact reference copies + исправленные defaults и board profile |

В 0.5.0 query перемещён в `core/src/query.c`, public API — в корневой `include/quanta/`.
Manifest SDK и host-тестов обновлён вместе. Публичные размеры/ABI прежних объектов метрик
сохранены, а объекты синхронизации теперь непрозрачны — нужна полная пересборка компонента.
Исторические копии настроек платы не участвуют в сборке. Рабочий компонент не компилирует старый provider API.

## Сохранённые исправления 0.4.0 и ограничения

**VDD33.** SDK документирует единицы 1/1024 V, а не mV. Теперь `(raw * 1000 + 512) / 1024`;
raw 0/65535 -> NO_DATA. По умолчанию отключено (UNSUPPORTED, не 0). Для включения нужны
`CONFIG_QUANTA_MEASURE_VDD33=y`, `CONFIG_ESP_PHY_INIT_DATA_VDD33_CONST=255` и физически
неподключённый TOUT. Нельзя включать это вслепую на плате с подключённым ADC. Wi-Fi stack
самостоятельно не запускается. При включении с PHY setting !=255 сборка выдаёт явную ошибку. `semantic_version` этой метрики поднята до 2.

**Chip ID.** Используется factory/eFuse MAC, доступный без инициализации Wi-Fi, а не текущий
runtime STA MAC. Формат — прежнее 24-bit число, но переопределённый пользователем STA MAC
больше не меняет его. `semantic_version=2`, SENSITIVE. Это не криптографически уникальный ID.

**Config.** В исходном defaults строка main-stack была склеена с PHY VDD setting.
Исправлено. Exact originals доступны в `firmware/esp8266/reference/` и не подаются в SDK.
В `profiles/original-lab.defaults` собраны аппаратные предположения прежнего примера:
160 MHz, 2 MB flash, DIO, 26 MHz XTAL, VDD opt-in. Они требуют проверки по вашей плате.

**OSAL.** Используются SDK 64-bit monotonic microseconds, а не приватный tick-wrap accumulator.
Sleep округляется как минимум до одного tick. Mutex/condition/thread — SDK pthread
adapter с непрозрачными handle в общем `include/quanta/osal.h`; прежняя схема с binary semaphore вместо полноценного broadcast не переносится.
Файловая система в этом приложении не подключена, RTC/SNTP не настроен: file API сообщает
недоступность, UTC — unavailable. Это не эмуляция FAT/SPIFFS или календарных часов.

**Serial.** U64/INT64_MIN печатаются без зависимости от newlib 64-bit printf; сохранены шесть
дробных знаков для конечных float в поддерживаемом диапазоне |x| < 1e12. Ошибка/NaN не
превращается в успешное число. App использует low-memory `quanta_metric_read_once`.

## Сборка с настроенным SDK (Linux либо Windows SDK shell)

Нужен **ESP8266_RTOS_SDK**, не SDK ESP32. Исходники сверены с API tag **v3.4** и его рекомендуемым
Xtensa LX106 GCC 8.4.0. Нативная линковка этой ревизии с SDK здесь НЕ выполнялась.

Подготовьте SDK и submodules, пользуясь [официальным README v3.4](https://github.com/espressif/ESP8266_RTOS_SDK/tree/v3.4).
Ни SDK, ни toolchain не включены в архив. Пример получения исходников:

```bash
mkdir -p "$HOME/esp"
cd "$HOME/esp"
git clone --branch v3.4 --recursive https://github.com/espressif/ESP8266_RTOS_SDK.git
export IDF_PATH="$HOME/esp/ESP8266_RTOS_SDK"
# Каталог bin распакованного toolchain должен быть в PATH:
export PATH="$HOME/esp/xtensa-lx106-elf/bin:$PATH"
xtensa-lx106-elf-gcc --version
```

Используйте отдельное совместимое Python-окружение SDK, а не системный Python вслепую.
В v3.4 requirements ограничивает pyparsing `<2.4.0`; совместимость с современным Python нельзя
считать автоматической. Сначала проверьте `idf.py --help` и штатный SDK hello_world в этом
окружении. Не обновляйте весь requirements произвольно ради прохождения pip.

Затем из корня Quanta в этом **уже настроенном SDK shell**:

```bash
cd firmware/esp8266
python "$IDF_PATH/tools/idf.py" menuconfig
python "$IDF_PATH/tools/idf.py" build
python "$IDF_PATH/tools/idf.py" size
python "$IDF_PATH/tools/idf.py" -p /dev/ttyUSB0 flash monitor
```

Порт `/dev/ttyUSB0` — пример; выберите фактический. Выход из SDK monitor — по его подсказке.
Во время `menuconfig` проверьте flash size/mode, XTAL, CPU clock и пункт Quanta firmware.
Не выполняйте `erase_flash` по умолчанию: он может удалить чужие данные платы.

PowerShell в настроенном Windows SDK-окружении:

```powershell
$env:IDF_PATH = 'C:\esp\ESP8266_RTOS_SDK'
# В PATH уже должны быть совместимый Python и xtensa-lx106-elf/bin.
Set-Location firmware\esp8266
python "$env:IDF_PATH\tools\idf.py" menuconfig
python "$env:IDF_PATH\tools\idf.py" build
python "$env:IDF_PATH\tools\idf.py" size
python "$env:IDF_PATH\tools\idf.py" -p COM5 flash monitor
```

Для ESP используйте отдельный checkout/build path без пробелов: простота путей нужна и самому
старому SDK, не только нашему компоненту. VS desktop preset не собирает Xtensa firmware.

## Возврат исходного lab profile

Только после проверки платы. Сначала сохраните свой `sdkconfig` и прежний build вне проекта.
SDK v3.4 ожидает один defaults-файл: объедините оба файла в один, а не передавайте список путей.

```bash
cat sdkconfig.defaults profiles/original-lab.defaults > sdkconfig.lab.defaults
python "$IDF_PATH/tools/idf.py" -D SDKCONFIG_DEFAULTS=sdkconfig.lab.defaults menuconfig
python "$IDF_PATH/tools/idf.py" build
```

Defaults применяются при генерации отсутствующего sdkconfig; существующий SDK config имеет
приоритет. Для нового профиля начните в новой рабочей папке либо предварительно переместите
sdkconfig/build в резервную копию. Не удаляйте пользовательскую конфигурацию автоматически.

## Тесты на компьютере и приёмка платы

```bash
ctest --test-dir build/linux-default -R esp8266 --output-on-failure
```

Два executable (`enabled`/`disabled`) компилируют **тот же полный source/ABI manifest**, включая
app_main и форматтер, но SDK headers/calls подменены тестовыми. Проверяются 9 полей, units,
ошибки SDK, HAL GPIO, low-memory helper, engine batching, limits и 64-bit clock за границей
32-bit ticks. App_main компилируется, но бесконечный serial loop на хосте не запускается.

На реальной плате отдельно требуется: clean SDK build/link, size/map, прошивка, serial capture,
все девять значений/status, стабильный heap/min-heap при длительном запуске, stack high-water
mark, перезагрузка, VDD-off/on только при корректной схеме, GPIO только на безопасном пине.
Нельзя объявлять это пройденным по результатам host-тестов.
